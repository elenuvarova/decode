# Decode — правила дизайн-системы и токенов

> Дистилляция методологии DESIGN.md (формат Google Labs `design.md`) под Decode.
> Особенность нашего процесса: сначала **ч/б-серые wireframes**, дизайн сильно позже —
> поэтому архитектура токенов закладывается сразу, а значения стартуют grayscale.

## DESIGN.md — единственный источник визуальной правды

- Живёт в `docs/DESIGN.md` (создаётся на фазе дизайн-системы, ПЕРЕД UI-китом).
- Это **контракт**: любая правка дизайна = правка DESIGN.md в том же коммите.
- Никаких значений вне DESIGN.md: каждый цвет/отступ/шрифт в коде ссылается на токен.
- Формат: YAML front-matter (токены) + 8 markdown-разделов:
  `Overview → Colors → Typography → Layout → Elevation & Depth → Shapes → Components → Do's and Don'ts`.
- Проверка формата: `npx @google/design.md lint docs/DESIGN.md` (битые ссылки между
  переменными, порядок разделов) — чинится молча, пользователю показывается итог.

**Что такое токен:** именованное значение (`primary` вместо `#1A1C1E`, `spacing-md`
вместо `16px`). В Figma это variables, в DESIGN.md — tokens, в CSS — переменные
(`--color-primary`). Один концепт на трёх уровнях. Меняешь значение в одном месте —
обновляется весь UI.

## Цвета — ДВА уровня, обязательно

1. **Примитивы (palette)** — тупо именованные значения: `gray-50…900`, `blue-50…900`.
   Уникальные hex живут ТОЛЬКО здесь, нигде не повторяются.
2. **Семантические роли** — ссылки на примитивы по смыслу, БЕЗ дублирования hex:
   `background → white`, `foreground → gray-900`, `primary → blue-600`,
   `trap-flag → red-600`. Роль не содержит hex — она указывает на примитив.

Компоненты используют **только роли** (`bg-primary`, `text-foreground`), никогда
примитивы напрямую. Выгоды: перекраска = смена ссылок ролей в одном месте; тёмная
тема = те же роли на другие примитивы.

**Почему это идеально для нашего процесса:** на этапе wireframes все роли указывают
на grayscale-примитивы (`primary → gray-900`, `trap-flag → gray-700` + иконка/паттерн
для различимости). Когда позже придёт дизайн — меняются только ссылки ролей, ни один
экран не переписывается.

### Обязательный набор ролей (независимо от стилистики)

- **Surface:** `background`, `foreground`, `muted`, `muted-foreground`, `border`,
  `card`, `card-foreground`, `popover`, `popover-foreground`, `input`, `ring`
  (это роли, которые ожидает shadcn).
- **Brand:** `primary` + `primary-foreground` (контрастный текст поверх).
- **Semantic — у Decode точно есть** (наш продукт построен на статусах):
  `success`, `warning`, `error`/`trap`, `info` — каждый парой `<name>` + `<name>-foreground`.
  Кандидаты под домен: `trap-flag`, `confidence-high/medium/low`, `renewal-due`.
- **Тёмная тема планируется** (iOS-аудитория ждёт обе) → каждое цветовое значение
  сразу парой light/dark (`:root` и `.dark`).
- Для каждой пары текст/фон — WCAG AA: **4.5:1** для текста <18px, **3:1** для
  крупного текста и UI-элементов. `on-*`/`*-foreground` токены обязательны.

## Spacing — это контракт, не одно число

Именованная шкала, всё кратно базовому ритму, и **обязательно с usage** — какой шаг где:

```yaml
spacing:
  unit: 4px               # база; iOS-приложение → компактно-средняя плотность
  xs: 4px                 # внутри компонента: иконка ↔ текст
  sm: 8px                 # между близкими элементами
  space-12: 12px          # компактный тир: плотные пары, паддинг кнопки/чипа (добавлен 2026-06-26)
  md: 16px                # между элементами в блоке; горизонтальные поля экрана iOS
  space-20: 20px          # hero/feature-паддинг (добавлен 2026-06-26)
  lg: 24px                # padding карточки, между блоками
  xl: 32px                # между секциями экрана
  "2xl": 48px             # крупные разрывы (онбординг, empty states)
  screen-padding: 16px    # боковые поля экрана (iOS-стандарт)
```

Без usage-контракта экраны берут отступы «на глаз» и расходятся между собой. Один и
тот же тип отступа (padding карточки, gap между полями, разрыв секций) одинаков на
всех экранах — это и держит единый вид.

## Объём шкал — от референса, не от шаблона

Состав и количество ступеней каждой шкалы выбирается под стилистику (нет универсального
«N радиусов»). Ориентиры:

| Референс | Neutral | Типографика | Радиусы |
|---|---|---|---|
| Минимализм (Linear/Things) | 3–4 ступени | 4 уровня | 3 |
| Средний (Stripe/Apple) | 5–7 | 5–6 уровней | 4–5 |
| Богатый (Material) | 9–11 | 6+ | 5–6 |

**Decode (рабочая гипотеза):** средний уровень, ориентир — **Apple/Things**
(просторная плотность, мягкие радиусы 12–16px, лёгкие тени, выраженная иерархия
типографики) — органично для iOS. Подтвердить на фазе дизайна.

## Типографика (iOS)

- Системный стек SF Pro: `-apple-system, BlinkMacSystemFont, "SF Pro Text", system-ui, sans-serif`.
  Не подключать шрифты `<link>`-ом с CDN; кастомный шрифт (если появится) — через `next/font`.
  В Figma рампа собрана на **Inter** — стенд-ин SF Pro с близкими метриками (норма
  wireframe-фазы); в коде всегда системный SF Pro-стек.
- Уровни — только реально нужные продукту. Для Decode: `display` (headline-число
  кокпита), `h1/h2`, `body`, `caption` + **`figures`/`figures-lg` (tabular-nums) для сумм,
  процентов и дат** — финансовые числа обязаны выравниваться.
- Размеры в rem (уважение к Dynamic Type). Минимум body — 17px-эквивалент (iOS-норма).

## Остальные шкалы — минимум в любом случае

- **Радиусы:** хотя бы `DEFAULT`; ступени — если встречаются в стилистике.
- **Тени:** хотя бы одна, если есть card/sheet/popover; flat → фиксируем `elevation: flat`.
- **Z-index:** явные слои ровно под организмы продукта (sheet, modal, toast, dropdown).
- **Animation:** хотя бы `duration` (fast 150ms / normal 250ms / slow 400ms) + easing,
  либо `motion: none`. Хардкод длительностей в коде запрещён.
  `prefers-reduced-motion` — обязательный фолбэк.

## Синхронизация токенов с Tailwind v4 — частая поломка

⚠️ В Tailwind v4 `tailwind.config.ts` по умолчанию **не читается**. Токены идут в
`src/app/globals.css`:

```css
:root { --background: …; --primary: …; --radius: 12px; }
.dark { --background: …; --primary: …; }

@import "tailwindcss";
@theme inline {
  --color-background: var(--background);
  --color-primary: var(--primary);
  /* …все роли DESIGN.md… */
  --radius-md: var(--radius);
}
```

Цепочка одна: примитив → семантическая роль → класс (`bg-primary`).
Проверка что подцепилось: Foundations на `/style-guide` показывает реальные цвета,
кнопки берут свой `bg-primary`. Всё серое/дефолтное → токены не привязаны.

## Wireframe-фаза: правила применения

1. Палитра примитивов = `gray-50…900` + один placeholder-акцент (тоже серый, но
   именованный `primary` — чтобы semantic-роли существовали с первого дня).
2. Различимость статусов (trap/success/warning) в ч/б — через иконку, вес шрифта,
   заливку/обводку, НЕ через цвет (бонус: это сразу прокачивает доступность —
   colorblind-safe по построению).
3. Типографика, spacing, радиусы, z-index, motion — настоящие с первого дня
   (это и есть скелет wireframes).
4. Тени на wireframes — минимальные или flat; включаются на фазе дизайна.

## Финальная сверка DESIGN.md (показывать не «количества», а покрытие)

- Цвета: brand, neutral (N ступеней), surface roles, semantic — что покрывает каждая группа
- Типографика: перечислить уровни
- Радиусы / Spacing (unit + шкала) / Тени / Z-index / Анимации
- Component refs в YAML (button, card, input, …)
- Lint: passed
- Контраст ключевых пар ≥ 4.5:1

Если категория не покрывает нужный сценарий — токены добавляются СЕЙЧАС, не на этапе
экранов. Сочинение токенов на лету при сборке экранов запрещено.
