# Decode — экранные контракты, интерактивность и верификация

> Дистилляция методологии (промпты 05–09) под Decode: iPhone-first, последняя iOS.
> Эти правила включаются на фазе wireframes/прототипа и действуют до конца проекта.

## Один файл на экран: `docs/screens/<url>.md`

Обзорная карта экранов (`docs/ux/screen-sitemap.md`) превращается в поэкранный
контракт ДО первой строки JSX. На каждый экран один файл, в нём ВСЁ:

**Логика** (из продуктовой фазы):
- Доступ (кто видит), данные (какие сущности/поля)
- Состояния: `default · loading · empty · error · success` — все пять, явно
- Действия по элементам — с конкретным результатом: «Tap "Scan" → камера →
  после捕 capture → /processing», не «кнопка сканирования»
- Связи с другими экранами, валидация форм

**`## Визуал`** (заполняется на фазе wireframes):
- **Layout Mobile — основной** (iPhone 393×852): структура сверху вниз, sticky-элементы
  (TabBar, нижний CTA с safe-area), что скрывается/сворачивается
- Layout Desktop — вторичный (max-width, как растягивается)
- Компоненты сверху вниз: `<имя>` → компонент `shared/ui/<Name>` (variant, size, токены)
- Визуальные состояния: что показываем в loading (skeleton/спиннер), empty
  (иконка + текст + CTA), error (текст + retry)
- Edge cases визуально: длинный текст, пустой список, 100+ элементов
- `TODO: <что> + вопрос пользователю` — для всего, что не решено

**Принципы:**
- Двух источников правды по экрану не бывает: логика и визуал в одном файле.
- Деталь не описана → `TODO` + вопрос, НЕ молчаливый дефолт. Каждое AI-решение
  по дефолту явно помечено в секции — видно, где принять решение.
- Запрещённые слова (сигнал ухода в интерпретацию): «адаптируй», «возьми за основу»,
  «примерно как», «упростим», «как обычно делается».
- После цикла по всем экранам — обязательный вопрос пользователю «Что упустил?»
  Это главная точка валидации до кода.

## Дисциплина интерактивности прототипа

Закрывает три классические дыры: «mobile не сделан», «кнопки не работают»,
«выбираю фильтр — ничего не меняется».

1. **Mobile сразу с desktop, в одном компоненте.** Базовые классы — mobile-first
   значения, `md:`/`lg:` — desktop-override. Никаких `MobileX.tsx` + `DesktopX.tsx`
   (исключение — реально разная структура, тогда `hidden md:block`).
2. **Каждый интерактивный элемент имеет handler с видимой реакцией.** Ни одного
   `onClick={() => {}}`, ни одного `<Input>` без `onChange`. Нет реальной логики →
   mock-action: `router.push('/...')`, `setState`, `toast.info('В разработке')`.
3. **Интерактивность данных через mock-state.** Фильтры/поиск/выбор — `useState` +
   `useMemo` над моками. Пользователь выбрал фильтр → видимый список перерендерился.
   Прототип реагирует на ввод, а не статично рендерит моки.
4. **Моки — в `entities/<e>/api/mock-*.ts`** через хуки (`useDocuments`,
   `useCommitments`) — подключение бэкенда не трогает экраны.
5. **По одному экрану за проход**, между группами — `/clear`. Порядок: онбординг →
   основной слой (overview, scan, result) → редкие (settings, ошибки).
6. **Курсор** (web-прототип): интерактив — `cursor-pointer` в `cva()`, disabled —
   `cursor-not-allowed` (Tailwind 4 убирает руку с `<button>` по умолчанию).

## Верификация — блокирующие проверки

### Greps после каждого экрана (всё → пусто, иначе чинить до перехода дальше)

```bash
# Хардкод цветов/размеров
grep -rE '#[0-9a-fA-F]{3,8}|\[\d+px\]' src/pages/<screen>/
# Пустые обработчики
grep -rE 'onClick=\{[()=>\s]*\}|onClick=\{undefined\}' src/pages/<screen>/
# Кнопки без действия
grep -rE '<(button|Button)\b' src/pages/<screen>/ | grep -v 'onClick\|href\|type="submit"\|asChild'
# Input без onChange
grep -rE '<Input\b' src/pages/<screen>/ | grep -v 'onChange\|readOnly\|disabled'
# Raw HTML вместо кита
grep -rE '<(button|input|select|textarea)\s' src/pages/ src/widgets/ src/features/
# Обвязка просочилась в страницы (должна быть только в layout)
grep -rnE "<(Header|TabBar|Footer)\b" src/pages/
# Внутренние ссылки через <a> (полная перезагрузка)
grep -rnE '<a [^>]*href="/' src/pages/ src/widgets/ src/features/
```

### Playwright-прогон — наши ширины (iPhone-first)

После сборки каждого экрана, скриншоты на: **375 × 667** (нижняя граница),
**393 × 852** (iPhone Pro — базовый), **430 × 932** (Pro Max), 1024+ (desktop-проверка).
Чек-лист на каждой ширине:
- нет горизонтального скролла; текст не вылезает за контейнер
- блок не «мистически узкий» на широком / широкий на узком
- tap-targets ≥ 44×44; нижние CTA/TabBar не перекрыты home-indicator (safe-area)
- sticky-элементы не перекрывают контент; картинки масштабируются пропорционально

### Прогон с extreme content (ломается именно на узком вьюпорте)

- Имя/название: «Иван» и «Александрина-Кристина Воронцова-Дашкова-Орлова»
- Список: 1 элемент, 100 элементов, пустой (empty state виден и читаем)
- **Финансовые форматы Decode:** `£1,234,567.89`, `−12.5 %`, representative APR
  `39.9% APR (variable)`, длинные названия мерчантов в строке коммитмента
- Статус-pill с длинным текстом («Ожидает подтверждения оплаты») — не распирает строку
- Toast/alert с текстом + кнопкой на 375px — не наезжают друг на друга
- Длинные неразрывные строки (URL, email в контенте) — `overflow-wrap: break-word`
- Даты UK-формата («29 May 2026, 14:30») помещаются в свои слоты
- Граничные значения: `0`, отрицательное, прочерк «—» — осмысленно, не дырой

Любой провал — СТОП, чинить **в компоненте кита**, не локальным override на странице.

## UX-аудит (перед переходом к данным/деплою)

По каждому экрану из sitemap — 5 проверок:
1. **Точки входа:** кто ссылается на экран? Нет ссылок → «призрак»: добавить вход или удалить.
2. **Точки выхода:** есть навигация с экрана? Нет → тупик (на iOS особенно критично:
   нет браузерной кнопки «назад» в standalone PWA).
3. **Интерактив:** у каждого элемента есть поведение (greps выше).
4. **Заглушки:** `TODO|coming soon|в разработке` — не показываем пользователю.
5. **Состояния:** loading/empty/error из контракта экрана реализованы.

Отчёт → `docs/ux-audit-<дата>.md`: 🔴 критические (блокируют переход дальше) /
🟡 доработки. Правило: дальше нельзя, пока есть хоть одна 🔴.

## Сверка спеки с кодом (смысловая)

Экраны spec ↔ слайсы `pages/` совпадают в обе стороны; поведение из контрактов
реализовано; поля моков = модель данных (новых полей в моках, которых нет в спеке,
быть не должно). Расхождение = либо код ушёл вперёд (обнови спеку), либо спека
описывает несуществующее (доделай или убери). Список расхождений показывается
пользователю с решением по каждому.

## Сохранение сессий

После завершённого этапа/фичи — session-файл в `docs/memory/sessions/<дата>-<slug>.md`
(что сделано, изменённые файлы, принятые решения с «почему», находки, открытые
вопросы) + обновление `docs/memory/state.md` (текущая фаза, ≤80 строк). Для Decode
это двойная ценность: «принятые решения + почему» — прямое сырьё для Notion case study.
