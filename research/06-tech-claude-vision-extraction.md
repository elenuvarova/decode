# Claude API для document understanding в Decode

**Трек:** tech-claude-vision · **Дата ресёрча:** 10 июня 2026 · **Источники:** официальная документация platform.claude.com (проверена live), arXiv, отраслевые бенчмарки. Все цены в USD, на дату ресёрча.

---

## TL;DR

- Все актуальные модели Claude (Fable 5, Opus 4.8/4.7/4.6, Sonnet 4.6, Haiku 4.5) поддерживают vision и нативный PDF-инпут. PDF обрабатывается как «текст + изображение каждой страницы».
- Стоимость обработки одного документа Decode (2–5 страниц): **~$0.02–0.03 на Haiku 4.5, ~$0.05–0.09 на Sonnet 4.6, ~$0.11–0.20 на Opus 4.8**. Cost-per-user-month при активном использовании — **порядка $0.6–1.5**, что комфортно вписывается в freemium £3–8/мес.
- **Рекомендация: Claude Sonnet 4.6** как основная модель (точность на числах — продуктово-критична), Haiku 4.5 — как cost-down после прохождения eval, Opus 4.8 — эскалация для сложных документов.
- Критичный архитектурный факт: **Citations (source highlighting) несовместимы со Structured Outputs** в одном запросе (API вернёт 400) и **не работают для фото и сканов без текстового слоя**. Это диктует двухвызовную архитектуру: extraction (structured output) + Q&A (citations) — отдельно.

## 2. PDF support: лимиты и как считаются токены

Источник: [PDF support docs](https://platform.claude.com/docs/en/build-with-claude/pdf-support) (проверено live 2026-06-10).

| Параметр | Значение |
|---|---|
| Максимальный размер запроса | **32 MB** (весь payload, включая всё остальное) |
| Максимум страниц на запрос | **600** (100 — для моделей с 200k контекстом, т.е. Haiku 4.5) |
| Формат | стандартный PDF без пароля/шифрования |
| Способы передачи | URL / base64 в `document`-блоке / **Files API** (`file_id`, beta `files-api-2025-04-14`, файл хранится до удаления, до 500MB) |
| Совместимость | prompt caching ✅, Batch API ✅, tool use ✅, citations ✅ (только если есть текстовый слой) |

**Как это работает и как тарифицируется.** Система конвертирует **каждую страницу в изображение** и параллельно **извлекает текст** страницы; модель видит и то и другое. Токены = текст + изображение:

- **Текст: ~1,500–3,000 токенов на страницу** в зависимости от плотности (официальная оценка из доков).
- **Изображение страницы:** по обычной vision-формуле (см. §3), на Sonnet/Haiku — до ~1,568 токенов/страница.
- Никаких отдельных «PDF fees» нет — обычный input-token pricing. Точную оценку для конкретного PDF даёт бесплатный endpoint [`count_tokens`](https://platform.claude.com/docs/en/build-with-claude/token-counting).

Итого реалистичная оценка для финансового документа: **~3,000–4,500 токенов на страницу PDF** (текст + изображение).

Практические рекомендации из доков: размещать PDF **до** текста промпта, использовать prompt caching при повторных запросах к тому же документу, для больших PDF — Files API, чтобы не раздувать payload.

Для Decode лимиты не проблема: 2–5 страниц — это <25K токенов, любые модели справляются с запасом (даже Haiku со 100-страничным лимитом).

## 3. Vision (фото документов): лимиты и токены

Источник: [Vision docs](https://platform.claude.com/docs/en/build-with-claude/vision) (проверено live).

- **Формула токенов: `tokens ≈ width × height / 750`** (пиксели).
- Cap по токенам на изображение: **1,568 токенов** (≈1.19 мегапикселя, длинная сторона ≤1568px) для Sonnet 4.6 / Haiku 4.5 / Opus 4.6; **4,784 токена** (≤2576px) для Opus 4.7/4.8 / Fable 5. Изображения больше — автоматически даунскейлятся.
- Форматы: JPEG, PNG, GIF, WebP. Максимум 10 MB на изображение (base64), до 100 изображений на запрос (200k-модели) / 600 (1M-модели); **при >20 изображений в запросе лимит размера падает до 2000×2000px**.
- Стоимость примеров (Sonnet, $3/MTok): фото 1000×1000 ≈ 1,334 токена ≈ **$0.004**; всё, что ≥1.19MP — ≈1,568 токенов ≈ **$0.0047** за страницу-фото.
- Официальные предупреждения по качеству: мелкий текст должен быть читаем, тяжёлая JPEG-компрессия портит распознавание текста, повёрнутые изображения снижают качество — **предпочтительно ресайзить/выравнивать на клиенте до отправки**.

**Вывод для Decode:** на камере телефона делать клиентский препроцессинг (crop по границам документа, deskew, контроль glare/shadow в реальном времени при съёмке — стандартная практика, см. [TableFlow](https://tableflow.com/blog/image-to-data), патенты на real-time glare analysis) и ресайз до ~1568px по длинной стороне → предсказуемые ~1,500 токенов/страница на Sonnet/Haiku.

## 4. Pricing и стоимость обработки 1 документа для Decode

Источник цен: [Pricing docs](https://platform.claude.com/docs/en/about-claude/pricing) (проверено live 2026-06-10).

### Допущения (per-document, сценарий Scan → Understand)

- Системный промпт + инструкции + few-shot: ~2,000 токенов (кэшируется).
- Документ: PDF-страница ≈ 3,500 ток. (текст+изображение); фото-страница ≈ 1,600 ток.
- Выход: structured JSON (3-sentence summary + key terms + traps + поля для true-cost engine) ≈ 2,000 токенов.

### Стоимость одного документа

| Сценарий | Input ток. | Haiku 4.5 | Sonnet 4.6 | Opus 4.8 |
|---|---|---|---|---|
| 3 фото (камера) | ~7,000 | **$0.017** | **$0.051** | ~$0.10* |
| PDF 3 стр. | ~12,500 | **$0.022** | **$0.067** | $0.11 |
| PDF 5 стр. | ~19,500 | **$0.029** | **$0.088** | $0.15 |

\* на Opus 4.8 фото в high-res стоят до 3x больше image-токенов; при даунсемпле до 1568px — сопоставимо с Sonnet по токенам, но дороже по ставке.

### Q&A-тёрн («ask anything» по закэшированному документу, Sonnet)

Документ закэширован при первом скане (cache write 1.25x ≈ +$0.01 к первому вызову): cache read 12.5K ток. × $0.30/MTok ≈ $0.004 + вопрос + ответ ~400 ток. × $15/MTok ≈ $0.006 → **~$0.01 за вопрос**.

### Cost-per-user-month (оценка)

| Профиль | Использование | Haiku-extraction + Sonnet-Q&A | Всё на Sonnet 4.6 |
|---|---|---|---|
| Free-пользователь | 2 дока/мес, 2 вопроса | **~$0.07** | ~$0.16 |
| Платный, средний | 8 доков/мес (4 стр.), 5 вопросов/док | **~$0.6–0.8** | **~$1.1–1.3** |
| Платный, power | 20 доков/мес, 8 вопросов/док | ~$1.5–2.0 | ~$3.0–3.5 |

При цене подписки £3–8/мес (≈$3.8–10) COGS на инференс у среднего платного пользователя — **10–30% выручки на Sonnet, <10% на Haiku-гибриде**. Юнит-экономика сходится с большим запасом; «средние» цифры стоит закладывать в P&L с буфером ×1.5 на ретраи и рост глубины Q&A.

### Прочее из прайса, что важно знать

- Prompt caching: write 5m = **1.25x** input, write 1h = **2x**, read = **0.1x**. Минимальный кэшируемый префикс: 2,048 ток. (Sonnet 4.6), **4,096 ток. (Haiku 4.5 и Opus 4.5–4.8)** — короткий системный промпт на Haiku молча не закэшируется.
- Batch API: **−50% на input и output** (Sonnet: $1.50/$7.50).
- Tool use добавляет 290–675 токенов системного промпта в зависимости от модели.
- 1M контекст на Sonnet 4.6/Opus — по стандартной цене, без long-context премии (Decode это не нужно, но приятно).

## 5. Structured outputs / tool use для извлечения полей

Источник: [Structured outputs docs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs) (проверено live). Статус: **GA** на Opus 4.8/4.7/4.6/4.5, Sonnet 4.6/4.5, Haiku 4.5.

Два механизма:

1. **JSON outputs** — `output_config.format` с `json_schema`: ответ модели **гарантированно** валидный JSON по схеме (constrained sampling). Это правильный механизм для Decode-extraction: поля key terms → детерминированный true-cost engine без `JSON.parse`-ошибок и ретраев. В Python SDK — `client.messages.parse()` с Pydantic-моделью.
2. **Strict tool use** — `strict: true` на tool-схеме: гарантированно валидные аргументы инструментов. Нужен, если extraction строится как tool-calling (для Decode проще JSON outputs).

Ограничения схем, критичные для дизайна экстрактора Decode:

- **Не поддерживаются числовые ограничения (`minimum`/`maximum`/`multipleOf`) и строковые (`minLength`/`maxLength`)** → валидацию диапазонов (APR 0–199%, дата в будущем и т.п.) делать на клиенте/бэкенде поверх ответа.
- `additionalProperties` обязан быть `false`; рекурсивные схемы нельзя; enum только из примитивов.
- Первая компиляция схемы добавляет latency; скомпилированная грамматика **кэшируется 24 часа** — держать схему стабильной (изменение `description` кэш не сбрасывает, изменение структуры — сбрасывает).
- Лимиты сложности: ≤20 strict-tools, ≤24 optional-параметра, ≤16 union-параметров.
- Работает с Batch API и streaming. **Несовместимо с citations** (см. §6).

## 6. Citations — готовый механизм source highlighting для Q&A

Источник: [Citations docs](https://platform.claude.com/docs/en/build-with-claude/citations) (проверено live). Это прямое попадание в фичу Decode «ask-anything Q&A with source highlighting».

- Включается `citations: {enabled: true}` на `document`-блоке. Ответ приходит как чередование text-блоков и привязанных citations: для **PDF — номера страниц (1-indexed)**, для plain text — символьные диапазоны, для custom content — индексы блоков.
- `cited_text` (точная цитата) **не тарифицируется как output-токены** — дешевле и надёжнее, чем просить модель цитировать промптом; по оценке Anthropic citations значимо точнее prompt-based цитирования.
- Совместимо с prompt caching (кэшировать сам document-блок) и Batch API.
- **Два жёстких ограничения:**
  1. **Citations + Structured Outputs в одном запросе = ошибка 400.** Поэтому extraction и Q&A — это два разных вызова с разной конфигурацией.
  2. **Цитируется только извлекаемый текст.** Image citations не поддерживаются: **фото документа (image-блоки) и сканированные PDF без текстового слоя нецитируемы.** Для фото-пути Decode source highlighting придётся строить самостоятельно: шаг 1 — полная транскрипция фото моделью, шаг 2 — Q&A по транскрипции как plain-text document с citations (символьные диапазоны → подсветка в UI поверх транскрипции).

Доверие (confidence) на уровне API не возвращается — «не найдено» как готовая фича; стандартная практика — запрашивать self-reported confidence per-field в схеме + верифицировать цитату string-match'ем по извлечённому тексту.

## 7. Prompt caching

Источник: [Prompt caching docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) + pricing (проверено live).

- Кэш — **префиксный**: любой байт-чейндж в префиксе инвалидирует всё после него. Порядок рендера: `tools` → `system` → `messages`. Системный промпт Decode должен быть заморожен (без дат/UUID внутри).
- Цены: write 1.25x (5 мин TTL) / 2x (1 час), **read 0.1x**. Окупается со второго запроса (5m TTL).
- До 4 breakpoint'ов; минимальный кэшируемый префикс — 2,048 ток. (Sonnet 4.6) / 4,096 (Haiku 4.5, Opus 4.5+); короче — молча не кэшируется.
- Проверка хитов: `usage.cache_read_input_tokens` в ответе.

Паттерн для Decode:
1. **Системный промпт + few-shot примеры** (стабильные) — breakpoint №1; экономит ~90% на этой части каждого вызова.
2. **Document-блок** — breakpoint №2 при первом скане; все последующие Q&A-тёрны в сессии читают документ из кэша за 0.1x. При типичной сессии «скан → 3–5 вопросов в течение пары минут» 5-минутного TTL достаточно; для «вернулся через час» — повторная оплата input один раз (это дешевле, чем платить 2x write «на всякий случай»).

## 8. Batch API

Источник: [Batch processing docs](https://platform.claude.com/docs/en/build-with-claude/batch-processing) (проверено live).

- **−50% к input и output** для любых Messages-запросов, включая PDF/vision/structured outputs/caching.
- Лимиты: до **100,000 запросов или 256 MB** на батч; большинство батчей завершаются **<1 часа**, максимум 24 часа (потом — `expired`, не тарифицируется); результаты хранятся 29 дней.
- Не подходит для интерактивного Scan→Understand (пользователь ждёт секунды, а не минуты-часы).

Применение в Decode:
- **Прогон eval-сетов** при каждом изменении промпта/модели (дёшево гонять 200+ документов).
- **Backfill Vault'а**: пере-extraction всех сохранённых документов при апгрейде схемы/промпта.
- **Renewal Radar enrichment**: периодические несрочные джобы (например, ежемесячный пересчёт/перепроверка condition'ов по документам).

## 9. Точность extraction из финансовых документов: best practices и типичные ошибки

### Что говорят исследования

- **FinCriticalED** (первый fact-level OCR-бенчмарк по финансовым документам, 859 страниц, 9,481 аннотированный факт): «numeric values and monetary units — наиболее уязвимые типы фактов»; высокая поверхностная OCR-точность **не гарантирует** сохранность decision-critical чисел; ошибки концентрируются в визуально сложных, смешанных layout'ах. [arxiv.org/abs/2511.14998](https://arxiv.org/abs/2511.14998)
- **OCR-галлюцинации на деградированных сканах**: VLM плохо распознают собственную неуверенность при размытии/бликах и «дорисовывают» правдоподобный текст из языковых приоров вместо отказа (бенчмарк KIE-HVQA на ID-картах и инвойсах). [«Seeing is Believing?», NeurIPS 2025](https://arxiv.org/abs/2506.20168)
- **Числовые вычисления — слабое место LLM**: в обзорах финансового документооборота extraction достигает ~90%+, а вот арифметика поверх извлечённого — заметно хуже; рекомендация «LLM извлекает, детерминированная система считает» ([Daloopa](https://daloopa.com/blog/analyst-best-practices/exploratory-financial-data-analysis-using-large-language-models), [arXiv: Information Extraction From Fiscal Documents](https://arxiv.org/html/2511.10659v2)). **Это напрямую валидирует архитектуру Decode: deterministic true-cost engine, а не «попроси модель посчитать».**
- Мульти-страничные/иерархические таблицы — известная зона деградации ([arXiv 2511.10659](https://arxiv.org/html/2511.10659v2)); сравнение vision-пути и text-parse-пути для инвойсов: [arXiv 2509.04469](https://arxiv.org/pdf/2509.04469).

### Типичные ошибки vision-моделей на сканах/фото (чек-лист для trap-листа QA)

1. Путаница визуально похожих символов: `0/O`, `1/l/7`, `5/S`, `8/B`; смещение десятичной точки/запятой (£1,000.00 vs £100.00).
2. Галлюцинация «ожидаемых» значений на нечитаемых участках (блик ровно на сумме) — модель уверенно подставляет правдоподобное число.
3. Перенос значения из соседней строки таблицы (row/column misalignment) — особенно в таблицах платежей.
4. Даты: UK-формат DD/MM/YYYY vs US MM/DD/YYYY; относительные формулировки («within 14 days of…»).
5. Проценты: путаница APR vs номинальная ставка vs monthly rate; «0% for 6 months, then 24.9%» — извлечение только одной из двух ставок.
6. Мелкий шрифт сносок (где и живут «ловушки») нечитаем после даунскейла до 1568px — связка с trap detector'ом особенно чувствительна к разрешению.

### Best practices (применимо к Decode)

- **Извлекать verbatim + normalized парами**: `{"raw_text": "24.9% APR (variable)", "value": 24.9, "type": "apr_variable"}`. Verbatim-цитата позволяет (а) дешёвую верификацию substring-match'ем по извлечённому тексту страницы, (б) показ пользователю «откуда взято».
- **Per-field confidence + evidence** в схеме; поля с low confidence → UX «не смогли разобрать — переснимите этот участок», а не тихая подстановка.
- **Детерминированные кросс-проверки** после extraction: monthly_payment × term ≈ total_amount_payable; APR в правдоподобном диапазоне; даты в хронологии; сумма кредита < total payable. Несошедшееся — флаг «проверьте сами» + запрос пересъёмки.
- **Клиентский препроцессинг фото** (см. §3): crop/deskew/glare-контроль при съёмке — самый дешёвый прирост точности.
- Изображения/PDF — **до** текста промпта (официальная рекомендация Anthropic).
- Двухпроходная схема для сложных документов: проход 1 — транскрипция страницы, проход 2 — extraction из транскрипции (упрощает верификацию и citations); для MVP достаточно одного прохода + verbatim-поля.
- Температуру крутить не нужно/нельзя (на Opus 4.7+ sampling-параметры вообще удалены из API); детерминизм формата обеспечивает structured output, а точность — eval-цикл.

## 10. Eval set для extraction accuracy (тема AI-PM курса)

Методологическая база: [Hamel Husain, «Your AI Product Needs Evals»](https://hamel.dev/blog/posts/evals/) и [LLM Evals FAQ](https://hamel.dev/blog/posts/evals-faq/); метрики — стандарт из document-AI литературы ([Invoice IE: Methods and Performance Evaluation](https://arxiv.org/pdf/2510.15727), [Google Document AI evaluate](https://docs.cloud.google.com/document-ai/docs/evaluate)).

### Конструкция eval-сета для Decode

1. **Golden set: 30–50 документов на wedge-тип** (credit/BNPL offers), с разметкой ground truth по каждому полю. Оси покрытия:
   - источник: чистый digital PDF / скан PDF / фото при хорошем свете / фото с бликом-перекосом-тенью;
   - издатели: 5–8 реальных UK-форматов (банковские pre-contract credit information / SECCI-подобные формы, BNPL T&C);
   - edge cases: 0%-промо со скрытой ставкой после, переменная ставка, мелкий шрифт сносок, многостраничная таблица платежей, не-финансовый документ (negative case → graceful reject).
2. **Метрики — field-level, а не «процент хороших ответов»:**
   - exact match для денег/процентов (после нормализации формата), normalized match для дат;
   - per-field **precision / recall / F1** (стандарт document extraction: поле считается ошибкой при любом расхождении значения);
   - для trap detector — это классификация: precision/recall по каждому типу ловушки отдельно (false positives «выжигают» доверие так же, как false negatives — деньги пользователя).
3. **Код-assertions, не LLM-judge, для extraction**: сравнение с ground truth — детерминированный pytest-стиль (Hamel: «unit tests for LLMs are assertions»). LLM-as-judge оставить только для качества 3-sentence summary (тон, простота языка) — и его сначала откалибровать на ~100 размеченных примерах.
4. **Процесс**: error analysis на реальных провалах → новые кейсы в golden set → прогон через **Batch API (−50%)** при каждом изменении промпта/схемы/модели → дашборд per-field accuracy по типам документов → регрессионный гейт перед релизом.
5. **Решение Haiku vs Sonnet — это eval-решение**: запустить обе модели на одном golden set; если Haiku даёт сопоставимый field-level F1 на числах/датах — мигрировать extraction на Haiku и зафиксировать порог деградации, при котором откатываемся.

Публичных бенчмарков «Claude на UK credit agreements» — **не найдено**; собственный eval-set обязателен и одновременно является сильным артефактом для портфолио senior-PM.

## 11. Рекомендованная конфигурация для Decode

**Модель:** `claude-sonnet-4-6` для production extraction и Q&A (лучший баланс точности на числах и цены: ~$0.07/документ); `claude-haiku-4-5` — кандидат на extraction после eval-подтверждения (~$0.02/документ); `claude-opus-4-8` — fallback-эскалация для документов, заваливших кросс-проверки (high-res vision помогает на мелком шрифте, но +3x image-токенов и дороже ставка).

**Архитектура вызовов (per document):**

```
Вызов 1 — EXTRACT (Sonnet 4.6):
  input:  [system (cache bp1)] + [document: PDF/images (cache bp2)] + инструкция
  config: output_config.format = json_schema (структура: summary, key_terms[],
          traps[], поля для true-cost engine; каждое значение = raw_text + value + confidence)
  далее:  бэкенд-валидация диапазонов + кросс-проверки + true-cost расчёт (детерминированно)

Вызов 2..N — Q&A (Sonnet 4.6, по запросу пользователя):
  input:  тот же кэшированный документ (PDF с текст. слоем → citations: enabled;
          фото → Q&A по транскрипции из вызова 1 как plain-text document с citations)
  выход:  ответ + page/char citations → source highlighting в UI
```

**Параметры:** structured outputs (GA, без beta-заголовков); prompt caching ephemeral 5m на system+document; streaming для Q&A (perceived latency); `count_tokens` для предиктивного контроля стоимости; Batch API для eval-прогонов и backfill.

**Экономика:** $0.05–0.09 за документ, ~$0.01 за Q&A-тёрн, ~$0.6–1.3 cost-per-paid-user-month → COGS ≤10–30% от £3–8/мес.

## Key takeaways for Decode

1. **Фича целиком реализуема на одном Claude API без OCR-вендора**: нативный PDF (текст+изображение каждой страницы), vision для фото, structured outputs для полей, citations для source highlighting — всё GA. Меньше движущихся частей в MVP.
2. **Юнит-экономика зелёная**: ~$0.07/документ на Sonnet 4.6, ~$1/мес на активного платного пользователя — при £3–8/мес inference-COGS не является ограничением прайсинга. Free tier (2–3 скана/мес) стоит копейки даже на Sonnet.
3. **Двухвызовная архитектура — не опция, а необходимость**: citations несовместимы со structured outputs (400). Wireframes должны отражать два режима: «карточка результата» (extraction) и «чат с подсветкой источника» (Q&A) — это разные API-вызовы с разными гарантиями.
4. **Путь «фото» и путь «PDF» дают разный UX source highlighting**: у PDF подсветка по номерам страниц из коробки; у фото citations не работают → подсветка строится поверх транскрипции (или в v1 показываем verbatim-цитату без точной геометрической привязки). Это надо заложить в дизайн экранов Q&A.
5. **Trap detector и числа — главный риск точности**: numeric values/monetary units — самые уязвимые типы фактов у VLM; на бликах модели галлюцинируют правдоподобные значения. Контрмеры в продукт: capture-гайд при съёмке (glare/skew), verbatim+confidence в схеме, детерминированные кросс-проверки, честный UX «не смогли разобрать — переснимите».
6. **«AI извлекает — код считает» подтверждено исследованиями**: extraction >90% достижим, арифметика LLM ненадёжна → детерминированный true-cost engine (ядро дифференциации Decode) — методологически правильное решение, можно смело выносить в нарратив кейса.
7. **Eval-set — это и инженерный гейт, и артефакт портфолио**: 30–50 размеченных UK-документов, field-level F1, код-assertions, прогоны через Batch API (−50%). Решение «Haiku vs Sonnet» принимается цифрами с этого eval'а, а не интуицией.
8. **Vault + Renewal Radar почти ничего не стоят в inference**: документ обрабатывается один раз; напоминания — детерминированная логика по извлечённым датам; периодические пере-анализы — Batch API за полцены.
